# Releases and outside work

[Architecture index](Intro.md) · [Release format](../format/release.md) · [Run architecture](runs.md)

P12 is complete; [its evidence](../verification/p12.md) records the shared package, desktop selection/Review, standalone planning/finalization, terminal intake, Sync and actual both-agent checks. V11-P09 will extend the existing flow with guided release choices and task target versions.

`releaseCandidates` derives completed, unreleased work from canonical actions and release records. Active selections reserve their members; cancellation releases the reservation. `createReleaseAction` takes displayed hashes and creates a ready Release at Plan, preserving member bytes and linking selected IDs. A private selection token prevents concurrent requests from claiming the same work; public actions remain authoritative. Pending runs/writes and invalid planning data refuse creation. New selections advertise reader 0.2.0.

The version-8 SQLite projection caches releases and candidates, retains complete snapshots during prepared writes and preserves undo tables during rebuilds. The app lists notes, included actions and tags. The draft-backed release wizard creates an action through classified history; new undo bodies exclude the private selection token because it is serialization bookkeeping, so an unrelated terminal release does not prevent undo. Locks and recovery journals remain outside history.

Structured Releases carry selected IDs, proposed version and tag. The versioned proposal record must match. `readPlan` retains exact hashes of all three plan files and extends the displayed revision with selection and record metadata/body. Final status/date are bookkeeping; version, tag, members and notes remain fixed. Review fingerprints and grouped guards include the record and selected action files. Changed proposals require new acceptance. The app displays the proposal and leaves acceptance at Review/Ready for the agent. Accepted release plans/notes also enter the decision projection.

The app creates no version bump, commit or tag. The runtime binds prepared files, members, version/tag and commit message in its private checkpoint. It uses a separate Git index, reuses matching run-trailer commits/tags and refuses conflicting tags or changed files. Release/members/run/checkpoint change in one durable group; verified dead-owner recovery reconciles this run’s prepared operation before Git/index effects. Prepared approved Release intent can resume its commit. Terminal intake collects and queues eligible work atomically with real Git identity. Sync behavior follows below.

Version re-planning retains the consumed prior draft as superseded history instead of deleting it. That history no longer reserves work and is visibly labeled Superseded.

Sync is implemented in the shared package and a Node Git adapter. It chooses a reachable sync revision, reads actual trailers, verifies the exact report HEAD/range and guards template values/profile hashes. Confirmed values remain protected. One durable group writes profile/proposals/record and consumption with a private serialization token; dead-owner retries recover only contained Sync receipts and preserve outside edits. The desktop reads a bounded outside-commit count and copies either agent’s Sync command, refreshing on existing Git/planning watchers. The index remains disposable; undo consumption persists in shared Sync records.

## v1.1.0 guided version and Done-ticket choice

`@voidra/release-engine` exports a narrow pure Xeploy version adapter and read-only `projectReleaseOptions`. The utility and bundled runtime `release-options` command use this same adapter. Pinned Xeploy 1.4.2 was checked against its published package and [source README](https://github.com/Hussain7Abbas/xeploy/blob/7d20192221f9dbf3bec8026872515ebcbe7151c2/README.md). The applicable stable local-release question offers Bug fix, Minor, Major and Custom. RC suffixes are removed for the existing final-release convention; custom versions must be canonical, safe integers and higher than current. Its interactive deploy/merge/push flow is never invoked.

The desktop wizard selects completed unreleased work, chooses a version and Markdown notes, then requires Keep/Move for the explicitly listed selected Done tickets assigned to the shown current version. Every step, invalid input, original source/member hashes and the choice form one private durable draft. Back/cancel/close/restart never creates a Release action. A changed package keeps the old draft visible and blocks submission until a new draft is explicitly started. Create writes planning records only.

`releasePreparation` records source path/current version/hash, proposed version, bump type, ticketChoice and exact current-version member IDs/hashes. Historical/unassigned selected members are excluded from target-version changes. Preparation joins the structured Release fingerprint and is displayed again at exact Review. Both approval APIs recheck source and ticket context. Accepted startup refuses stale context before ownership/consumption. Source bump preparation verifies the chosen manifest contains the approved next version. The private checkpoint carries the same preparation, and existing expected hashes protect member/source bytes throughout Git finalization.

Finalization atomically applies the release/run/checkpoint and member updates. Move changes targetRelease only for the shown subset; Keep preserves it. Both retain immutable releasedIn membership and duplicate-release prevention. Human checklist semantics remain. Existing matching commits/tags reconcile; conflicts stop. The existing grouped-operation recovery also completes a process death during the new ticket updates without another commit/tag.

The browser/preload import only `voidra/release-preparation`, a Node-free schema export. Package validation, source reads and Xeploy execute in the utility/standalone runtime. No project source or package bytes are sent to AI. Task-tracked standalone proposals require explicit preparation; if intake lacks a keep/move answer, the agent asks through the existing question gate. A revised report can include new preparation for fresh Review; it does not renew acceptance or rewrite history implicitly. Legacy accepted proposals remain compatible.

## Monorepo source settings

Release settings lives on Releases, with a native folder picker, editable relative search folder, an optional exact-package mode and the existing guarded task-tracking migration. Discovery supplies the highest numeric version inside the saved folder; source details show the actual winning manifest. `checkReleasePreparation` rediscovers the current source at proposal/approval boundaries, so another package overtaking the winner invalidates the old proposal even when the former winner's bytes are unchanged. Source bump preparation still checks the explicitly approved manifest and its next version. See [release identity](tasks.md).
