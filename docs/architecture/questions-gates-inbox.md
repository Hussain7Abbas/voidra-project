# Questions, gates and inbox

[Architecture index](Intro.md) · [Format API](../format/api.md) · [Phase P07](../../plan/phase-07-questions-gates-and-inbox.md)

Question rounds remain in each action's `questions.md`. The shared `answerQuestion` helper validates a displayed file hash, writes one answer with actor/time, and preserves other rounds and unknown fields. Partial rounds keep the action Waiting. Completing the round makes it Ready for the agent to resume, including at Plan or Review. Delegation is an answer, but its agent choice must be resolved before a plan/review decision. Question controls use native radio groups, explicit submit, labeled free text and an accessible saved summary. Outside edits refuse the save and offer reload; they never silently overwrite a draft. Reload disables the controls until a refreshed question revision has reached the form, preventing an immediate second selection from capturing the old revision.

An agent choice is shown alongside its originating question as an assumption, with reason, actor and time. Unresolved delegation explains that the next agent run will record its choice. P08 supplies that runtime behavior; P11 supplies changing a settled assumption through a new action.

Plan approval uses the exact bytes of requirements, blueprint and acceptance. The screen shows their Markdown, including goal, out-of-scope work, approach, testing seams, ADR proposals and acceptance criteria. A request for changes persists `planFeedback` with author/time and returns the action to Plan/Ready. `approveAction` guards all three files, action, questions and the absence of a run lock. Invalid plan files cannot be approved. Changes to any file, including formatting, appear as an expired approval with changed filenames and an effective Plan stage. This is a derived view: indexing never changes the source action to reconcile stale approval. A fresh approval writes the actual transition and archives the earlier approval. Completed action plans are history: if outside edits invalidate them, the app explains that the original files must be restored and scope changes requested through a new action. It does not reopen a terminal action.

`reviewRevision` fingerprints every file within the action directory in deterministic path order, including action metadata/body, questions, plans and run results. `decideReview` requires a completed result for Review, checks the displayed fingerprint, and guards all presented files in the grouped write. It records feedback on rejection. Implementation types rework in Implement, Research in Discovery, Release in Plan. A stale implementation plan instead routes back to its approval gate. Accepting implementation/Research finishes the action. Release acceptance remains Review/Ready and records the approved plan hashes; its next agent run owns commit/tag finalization. Neither review helper nor app creates source edits, Git commits or tags.

The version-6 disposable SQLite cache stores question rounds with each action. Prepared writes and unresolved run finalization retain the preceding complete snapshot. Gate commands allow only the specific stale-approval/stale-review diagnostics they can resolve; unrelated format errors, live locks and unfinished recovery disable them. Other mutation commands remain blocked by diagnostics. A decision may resolve one action while unchanged sibling actions retain stale gates: the writer permits those specific pending gates, while changed-action gates and every structural error remain blocking. Rollback can restore an unresolved gate but never authorizes work.

The Waiting for you inbox derives items from indexed actions/profile records. It groups open questions, plans, reviews, unfinished human checklists and inferred profile answers. Open questions take precedence over an action's other gate. The sidebar shows the derived item count; no separate inbox state is saved. Native buttons support Tab/Enter, and opening an item preserves a path back to the inbox. Inference confirmation displays its source and requires a non-null answer and the installed matching template.

The scripted fake-agent gate fixtures test only the app side. Their synthetic implementation commit identity is explicitly a fixture, not proof of a real Git commit or authenticated agent execution. P08 and P12 provide the actual skill/Git evidence. Existing P03 crash/commit fixtures still use the real standalone run helpers.
